# Password-hash collection and visible evidence — 2026-10-13

This follow-up preserves the earlier audit changes and implements both requested
behaviors: opt-in current account key collection and visible report values by
default. It does **not** establish successful hash recovery in the live lab.

## Implemented behavior

- `--collect-password-hashes` requests current LM/NTLM and available Kerberos
  long-term keys for the users/computers returned by the scoped LDAP inventory.
  The existing Impacket dependency supplies SMB/SAMR/DRSUAPI support. The supplied
  account is used without escalation, directory writes, service execution,
  RemoteRegistry or VSS. Password history, local secrets and ticket-response
  hashes are explicitly outside this collector's scope.
- `--hash-collection-timeout` bounds the entire isolated worker. Completed
  records survive timeout; failed and unattempted accounts remain distinguishable.
  Account/RID and key encoding are validated before accepting callback output.
  Upstream processing errors become incomplete evidence, not silent success.
- Reports and checkpoints retain values by default. `--redact-secrets` removes
  recognized credential assignments and collected hash/key fields. It is separate
  from `--mask-client-report`, which anonymizes identities. Old redacted snapshots
  cannot recover removed values. Redaction is pattern-based and is not a guarantee
  that arbitrary freeform prose contains no secret.
- HTML has a bilingual Password Hashes tab with counts, per-account status,
  values and errors. JSON preserves the structured result; DOCX/PDF include the
  collection and its evidence gaps. Findings-only CSV/NDJSON/CEF are unchanged.
  The existing private file writers are retained; bind passwords and worker
  diagnostic text are excluded from logs.
- Offline/resume reuse saved results and original timestamps. A failed requested
  collection returns exit code 2 even when LDAP inventory succeeds.

## Confirmed issues and fixes

1. **High — requested capability absent.** LDAP inventory and Kerberoasting target
   export did not recover account keys. `core/password_hashes.py` adds bounded
   DRS collection; permission/protocol failures remain explicit. Synthetic worker
   tests verify successful parsing, timeout, denial, missing inventory, scope
   limits, partial results and cleanup. The live success path remains unverified.
2. **Medium — requested values removed before publication.** The scan and report
   boundaries unconditionally redacted directory assignments, while SYSVOL
   inspection discarded values. The CLI now passes an explicit visibility policy
   through `AtilKurt.py`, `core/engagement_workflow.py`,
   `analysis/sysvol_analyzer.py` and `reporting/client_report.py`. Regression tests
   cover visible/redacted offline reports and checkpoints. Synthetic PDF text and
   DOCX XML preserve the exact unmasked key values.
3. **Medium — collection count missing from client reports.**
   `reporting/client_report.py` read `completed_queries`, but the diagnostic
   producer emits `query_count`; the paragraph renderer also omitted collection
   health. DOCX/PDF now include the actual count and failed-query count. The live
   export check finds 100 queries in both formats.
4. **Integration corrections found during development.** Impacket can silently
   return after failed SAMR preflight and log per-account processing failures.
   Preflight now runs explicitly, and an isolated diagnostic counter marks
   swallowed processing failures as partial. SID-based inventory selection is
   used; GUID fallback names include the actual NetBIOS domain. Impacket's legacy
   DES/RC4 algorithm labels are normalized. Identity anonymization no longer
   substitutes text inside retained hash values. These are adapter fixes tested
   with synthetic inputs; they do not resolve the lab's replication errors.

## Live lab evidence

Target: `192.168.1.13`, `lab.local`, supplied account `cuma`. No AD configuration
or credentials were changed.

- Default LDAP/389 authenticated and completed **100 queries, zero failed LDAP
  queries**: 104 users, 56 groups, 1 computer, 2 GPOs.
- Hash collection attempted **105 inventoried accounts; zero returned hashes**.
  The final per-account response was **8439 (`ERROR_DS_DRA_BAD_DN`)**. Separate
  read-only probes for the bind account returned 8440 with a SID reference and
  8439 with a full DN. These responses do not establish successful replication
  or account takeover. Missing replication authorization is a hypothesis; the
  exact server-side cause was not verified.
- LDAPS/636 reset the connection, including with certificate validation disabled.
  StartTLS returned `unavailable`. Explicit TLS never downgraded to LDAP.
- SYSVOL/NETLOGON inspection returned partial coverage: one skipped entry, zero
  files inspected. Reparse/referral protection was retained, so this is not
  evidence that policy files contain no credentials.
- English, Turkish and redacted reports each passed Chromium checks across
  **41 tabs**, **105 account-status rows** and **53 takeover evidence dossiers**;
  no severe console errors or external requests. Mobile navigation passed.

Microsoft defines 8439 as an invalid replication DN and 8440 as an invalid
replication naming context; neither label alone proves why this DC returned it.
See [Microsoft system error codes](https://learn.microsoft.com/en-us/windows/win32/debug/system-error-codes--8200-8999-).
